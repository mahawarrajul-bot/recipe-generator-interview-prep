1. The 2-minute pitch

Problem. LLMs write good-sounding recipes but cannot be trusted on hard constraints. A "vegan" recipe may contain honey or butter, a "30 minute" recipe may take an hour, and for allergies a wrong answer can hurt someone.

What it does. You type what is in your fridge in any format (2 eggs, eggs (3), some onions), choose diets and a time limit, and get recipes with a shopping list of what you are missing.

Core idea. The LLM proposes, deterministic code disposes. Claude writes the recipes. Plain Python checks every one for diets, excluded ingredients, time and structure. A failing recipe goes back to the model with the checker's own messages for repair (up to 2 times). If it still fails it is discarded and shown under "Rejected recipes". The model's own claims are never shown as badges.

Proof. Two full evaluation runs (50 queries × 2 models, 100 pairs each). The repair loop fixed 95 to 98% of recipes that failed the first check, and none of the 481 delivered recipes broke a rule.

Honest caveat to say yourself: the results use a 50-recipe hand-written sample dataset, not Food.com, and measure conformance to this project's checker, not real-world safety. It is not medical advice.

2. Architecture and request flow

Fridge text→ Normalizer→ Grounding (BM25 retrieval)→ Claude (tool use)→ Checker→ Repair loop ≤ 2→ Shopping gap→ Streamlit UI
  1. Normalize the messy pantry text into canonical ingredients with quantities and units.
  2. Ground: find real recipes from the dataset with similar ingredients and offer them to the model as inspiration only.
  3. Generate: ask Claude for N recipes, structured output via tool use with a JSON schema made from the Recipe pydantic model.
  4. Check every raw recipe. Any violation triggers a repair prompt containing the checker's messages.
  5. Discard recipes that still fail. Never pad the result with unverified recipes.
  6. Shopping gap is computed in Python (recipe minus pantry), never by the model.
  7. Render: scaling of servings is pure Python, so the slider changes amounts with no new model call.

Only step 3 (and repairs) touch the network. Normalizer, checker, retrieval and shopping gap are pure functions (constitution rule C-2).

Diet rules (from checker/rules.py)

  • Vegetarian forbids meat, red meat, poultry, pork, fish, shellfish, gelatin.
  • Vegan forbids all of that plus dairy, egg, honey and animal-derived items.
  • Pescatarian forbids meat and gelatin. Gluten-, dairy-, nut-, egg-, soy- and shellfish-free forbid their tags. Diets combine as a union.
  • Allergen diets (the six "-free" ones) fail closed. Lifestyle diets (vegetarian, vegan, pescatarian) are more lenient on unknowns.

5. The spec-driven process

Spec first. specs/ holds a constitution (principles, stack, layout), a domain model, and for each feature a requirements file, a design and a task list. Requirements have numbered acceptance criteria (UI-10, CHK-14, ...). Tests carry # covers: ID markers, so every criterion maps to a test.

Constitution principles: never trust the LLM on constraints; fail loudly, not silently; deterministic core; explainable methods; small and testable modules.

6. Testing

  • python -m pytest runs in about a minute with no network and no API key. The LLM is replaced by a scripted fake (tests/support/fake_llm.py).
  • tests/adversarial/ holds tricky cases, including a zero-false-negatives test for the checker.
  • tools/mutation_check.py breaks each rule on purpose; the tests must notice.
  • tests/live/test_live_smoke.py is the only test that calls the real API. Off unless RECIPEGEN_RUN_LIVE=1.
  • Limit to admit: the fake model shows the pipeline works, not how the real model behaves. That is what the evaluation is for.

What holds up: the repair loop fixed 95 to 98% of failures; no delivered recipe broke a rule.
What does not: any ranking of the models. Intervals overlap and identical runs differed by up to 2× in some violation counts, so one sample per query is noisy.
Rerun: run 2 followed a checker vocabulary fix (plain words such as "broccoli florets", "flax egg"). Recipes failing only on an unrecognised ingredient fell from 24 to 5 (Sonnet). That fall is not proven to be the fix, since the intervals overlap.
Audit: 20 delivered recipes read; 18 pass, 2 had wrong amounts ("the remaining 1 tsp" after half was used), which the checker cannot see. The verdicts were proposed by Claude and accepted by the project owner, not an independent human review.
Cost: one full run took about 42 minutes and 260 model calls (0.9M tokens in, 0.5M out).

8. Limitations and next steps

  • Sample dataset only; results say nothing about real Food.com data.
  • The checker measures its own rules, not real-world safety. Ingredient database coverage is finite (unknown items are flagged unverifiable).
  • Quantity logic errors ("the remaining 1 tsp") are invisible to the checker.
  • One sample per query, so model comparison is inconclusive.
  • Streamlit page driven by the test harness with a real key, but not clicked through in a browser.
  • Duplicates, not failures, are the main reason a query returns fewer than 3 recipes.
  • Next: independent human audit; prompt change so ingredient names carry no preparation instructions; fix for "remaining {id}" amounts; run on real Food.com data; multiple samples per query.

9. Live demo script (about 5 minutes)

  1. streamlit run app/streamlit_app.py. It loads with no key.
  2. Click Fill in a demo fridge (messy list, vegetarian, 45 min).
  3. Point at What I understood: green chips are known; tamarind paste is orange, not in the database, and the app says so.
  4. Generate recipes (paid call, ask before clicking). Narrate the stages: retrieve, ask model, check, repair.
  5. Move the Servings slider: amounts and shopping list change with no new model call.
  6. Tick Skip repair (demo), choose vegan, regenerate, and open Rejected recipes to show the checker catching a slip with the reason.
  7. Open Pipeline trace for calls, tokens, time.

No key needed: python -m recipegen.checker demo/bad_vegan.json --diet vegan --max-minutes 30 shows the checker rejecting a bad recipe.

11. Question bank

★ Why not just ask the LLM to follow the diet?
Models make confident mistakes: our first-run data shows 13 to 23% of recipes broke at least one rule on first attempt. For allergies that is unacceptable. So the model's output is treated as untrusted input and checked in code.
Follow-up: Isn't your checker also fallible? Yes. It only knows what its database knows, so unknown ingredients are flagged unverifiable, and allergen diets fail closed. It also cannot see logic errors such as wrong remaining amounts (audit found 2 of 20).
★ Explain the architecture in one minute.
Normalize pantry text → retrieve similar real recipes (BM25) → Claude generates via tool use → Python checker validates each recipe → failures go through a repair loop (max 2) → survivors get a shopping gap computed in Python → Streamlit shows them, with rejected ones listed separately.
★ What does "the LLM proposes, deterministic code disposes" mean here?
Only the generation step is non-deterministic. Pass/fail, shopping list, scaling and diet rules are pure Python functions with reasons attached to every verdict. The model never gets to certify its own output.
★ How does the repair loop work?
When the checker finds violations, the pipeline sends the model a repair prompt containing the original recipe and the checker's own messages, and asks for a corrected one. This repeats up to RECIPEGEN_MAX_REPAIRS (default 2). Still failing → discarded (GEN-8), never padded with unverified recipes (GEN-10).
Result: 95 to 98% of first-check failures were fixed.
★ What did your evaluation show, and what can't you claim?
Claim: after repair, 0 of 481 delivered recipes broke a rule; repair fixed 95 to 98% of failures. Cannot claim: that one model is better (overlapping intervals, run-to-run noise up to 2×), real-world safety, or anything about Food.com (we used a 50-recipe sample).
★ Why a sample dataset instead of Food.com?
Kaggle needs a login and the project must run offline for demo and tests. The 50 hand-written rows use Food.com's column layout, and every report and the app footer label the dataset as SAMPLE. Setting RECIPEGEN_DATA_PATH switches to the real file with no code change.
★ How do you handle an ingredient your database doesn't know?
It is shown orange in the UI and flagged UNVERIFIABLE_INGREDIENT in the checker. For allergen diets this fails closed (recipe rejected). For lifestyle diets the severity is lower. "Fail loudly, not silently" is constitution principle 2.
★ How do you know your tests are good?
Acceptance criteria are numbered and each test carries a # covers: ID marker; adversarial cases and a zero-false-negatives test target the checker; tools/mutation_check.py breaks rules on purpose to see whether tests fail. Admit: the fake LLM can't show real-model behaviour.
Why BM25 and not embeddings?
Inspectable, no infrastructure, enough for a 50-row sample. Retrieval is only inspiration, and correctness doesn't depend on it, since the checker validates the output anyway.
Why use tool use for structured output?
It returns JSON matching a schema generated from the pydantic Recipe model, avoiding free-text parsing. The schema is guidance only; the checker still validates the raw payload (malformed ones are MALFORMED_RECIPE).
How is the shopping list computed?
shopping.compute_gap subtracts pantry from recipe ingredients by canonical name, in Python. The model's own shopping suggestions are not used.
How does the servings slider work without calling the model?
render.py scales amounts, formats them, and expands {id} placeholders in step text, all deterministically. A DANGLING_REF check ensures every placeholder points to a real ingredient.
What are the most common failures?
Time exceeded, unrecognised ingredients (e.g. "broccoli florets" before the vocabulary fix), forbidden words in step text but not in the ingredient list, malformed references. Remaining ones are mostly preparation instructions written into ingredient names.
Why did you rerun the evaluation?
The first run revealed the checker was rejecting harmless words ("florets") and not recognising "flax egg". We fixed the vocabulary, changed nothing else, and reran with identical queries, models and prompts. Both runs are committed so the change is auditable.
Why is Haiku's rate unchanged while Sonnet's fell?
Haiku's remaining failures were mostly other kinds (e.g. text scan and structure errors), not vocabulary. And Sonnet's drop is not proven to be the fix since its intervals overlap.
Who audited the 20 recipes?
Verdicts were proposed by Claude and accepted by the project owner. It is not an independent human review, and this is stated at the top of audit.md. An independent audit is listed as not done.
How do you protect the API key and cost?
Key lives in git-ignored .env; missing key gives a clear message, not a stack trace (C-4). The app binds to localhost only. The eval harness needs --yes and prints its plan with a maximum call count first; --dry-run spends nothing.
Is this medical advice?
No. The disclaimer "Automated check based on a built-in ingredient database. Not medical advice. Always read product labels." is shown with diet and allergen results (C-5).
What would you do with more time?
Real Food.com data; several samples per query; independent human audit; prompt change for ingredient names and remaining-amount phrasing; browser click-through test of the UI; possibly embeddings for retrieval.
Why keep model names in one file?
Model IDs change. One place (config.py) means one edit, and a test enforces that no claude-... string appears elsewhere in src/.
What is the difference between "pipeline trace" and the report?
The trace is per request: model calls, tokens, time and each recipe's fate. The report aggregates 100 (query, model) runs into rates with intervals.
